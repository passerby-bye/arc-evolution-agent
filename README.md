# arc-evolution-agent

Arc-Bench 黑客松决赛（hackathon-evolution）提交的演进 agent，最终版本 v4x。

决赛任务是在一个已经存在的 Web 应用上做"演进"：每个任务有 10 个目标功能，其中 5 个是修改已有功能，
5 个是新增功能。平台用 Playwright 私有测试评分，每个功能 3 个场景，共 30 个测试。
agent 要在保留原有功能的前提下完成这 10 个功能，并预置测试场景用到的种子数据。

## 流程

入口是 `main.py`。

1. **准备**：清理上次运行留下的数据文件，建立 git 基线。
2. **基线快照**：用浏览器打开原应用的页面，记录每页的控件，作为回归检查的依据（`snapshot.py`）。
3. **选目标功能**：带 "Original Feature Description" 的是修改功能，其余是新增功能。
4. **修复阶段**：原应用里如果有需求控件只存在于没被接入的模块中，先把这些模块接回去
   （`repair.py`、`graph.py`）。
5. **种子数据**：一次请求写入场景 GIVEN 里点名的预置记录，代码逐条核对是否存在。
6. **逐个功能**：新增功能先做。
   - 新增功能交给 Octos 内核的工具循环实现（`octos_feature.py`、`octos_stdio.py`）。
   - 修改功能用两步编辑：先按代码索引定位，再对编号的代码片段做按行编辑
     （`change.py`、`edits.py`、`code_index.py`）。
   - 每个功能生成场景测试并运行（`structured_tests.py`、`qa.py`），失败就带着失败步骤、
     页面文字和页面错误进入修复轮。改坏应用的功能会回退到上一个 git 提交。
7. **收尾**：清理遗留问题，再跑一轮 QA 审查（`wholeapp.py`、`audit_gen.py`）。

## agent 设计

### 设计目标

演进任务的难点不是"写出功能"，而是"在一个几千行、别人写的应用里改对地方，同时不把原来的东西改坏"。
所以设计围绕三件事：

1. **只改该改的**：每次只给模型看与当前功能相关的少量代码，不把整个应用喂进去。
2. **改坏了能发现**：用编译、启动、浏览器快照、场景测试层层检查，模型只能修检查明确指出的问题。
3. **改坏了能退回**：每个阶段结束都做 git 提交，应用跑不起来就回退到上一个提交。

### 核心机制

**两步编辑：先定位，再按行改。**
`code_index.py` 不调用模型，直接从源码里抽出每个文件的函数、路由和界面文字。
第一步，模型根据功能里引号引用的控件名和代码索引，选出要改的文件和函数。
第二步，只把这些函数带行号的片段给模型，让它按行号输出替换。
这样上下文小、改动集中，也避免整文件重写时误删别的功能。

**编辑安全检查。**
`edits.py` 在落盘前检查每一处编辑：
- 改完括号不平衡的，拒绝。
- 改完 `node --check` 不通过的，拒绝。
- 超出给模型看过的行范围的，拒绝。
- 同一轮里互相重叠的编辑，拒绝。

被拒的原因会原样反馈给模型，下一轮重写。

**调用图引导的修复。**
`graph.py` 建立前端调用和后端路由之间的关系，能找出两类问题：
- 前端调用了但后端没有提供的接口。
- 需求控件只存在于没被接入任何页面的模块里。

修复阶段把这些具体问题交给模型。原应用自带的问题记为基线，不算到后续功能头上。

**浏览器快照做回归检查。**
`snapshot.py` 在改动前后各打开一次应用的页面，记录每页的控件、页面报错和 HTTP 错误。
改动后丢了原来控件的页面，会连同页面报错一起报给模型。
需求点名的全局控件也在这里检查，比如页头的 "Search" 搜索框、`<main>` 里的 "Sign in" 链接。

**新功能交给 Octos，修改功能用两步编辑。**
- 新增功能要建新页面、新接口，适合交给 Octos 内核的工具循环自己读代码、写文件、跑命令
  （`octos_feature.py`）。
- 修改功能是在现有代码上做小改动，用两步编辑更精确。
- Octos 一轮没完成时，自动换成两步编辑接着做。

**只从公开需求生成测试。**
`structured_tests.py` 根据每个场景的 GIVEN/WHEN/THEN 生成结构化步骤，再转成 Playwright 测试。
测试只能用需求原文里出现的名字和数值，不能凭空编造控件名。
生成的步骤会做规整，减少测试本身写错，例如：
- 单元格坐标点击统一转成 gridcell。
- 文本框之间的角色可以互换。

测试失败时，反馈给模型的不只是断言错误，还有失败的步骤、当时页面上的文字和页面报错。

**通用的无障碍约定。**
提示词里写明标准 ARIA 做法，因为测试按角色和可访问名称找控件。例如：
- 消息放在唯一的 `role="alert"` 区域。
- 菜单是按钮加 `role="menuitem"`。
- 对话框的名称等于标题。

这些约定对任何应用都成立，不针对某个具体任务。

### 不做的事

- **不手写针对具体任务的测试或代码**：所有检查和提示都是通用的。
- **不从平台的评分结果里推断隐藏测试**：测试只来自公开需求。
- **不提交不调用模型的回放包**：每次运行都由模型现场完成。

### 已知不足

- **单个功能耗时不固定**：Octos 一个功能可能做 5 分钟，也可能做 40 分钟。时间耗尽后排在后面的功能会被跳过，
  这是同一个包分数波动大的主要原因。给每个功能设硬性时间上限是下一步要做的改进。
- **已知问题过滤过宽**：阶段结束时剩下的问题会被当作已知问题，后续阶段不再提示。
  需求点名的全局控件也被一起过滤了，这就是 github 得 0 分的直接原因。

## 运行

依赖 Python 3.10+、Node.js、Playwright 浏览器，以及 `pip install -r requirements.txt`。

```bash
export OPENAI_BASE_URL=...   # OpenAI 兼容接口
export OPENAI_API_KEY=...
export MODEL=deepseek-v4-flash-vision-exp
python main.py <requirements 目录> --output-dir <原应用目录>
```

原应用目录下要有 `frontend/` 和 `backend/`。常用的可选环境变量：

| 变量 | 作用 |
|---|---|
| `EVO_OCTOS` | 设为 `0` 时新增功能也用两步编辑，不用 Octos |
| `EVO_OCTOS_TURN_SECONDS` | Octos 单轮时长上限，默认 1200 秒 |
| `EVO_ONLY` | 只做指定的功能，逗号分隔，用于本地实验 |
| `EVO_SKIP_QA` | 跳过收尾 QA |
| `OCTOS_BIN` | 使用本地的 Octos 可执行文件，不下载 |

## 平台成绩

| 任务 | 通过 |
|---|---|
| sheet | 21/30，另一次运行 14/30 |
| github | 0/30 |

github 0 分的原因已经查明：首页 `<main>` 里缺 "Sign in" 链接，页头缺 "Search" 搜索框。
这两项检查在修复阶段就报出来了，但之后被当作已知问题过滤掉，最后的清理阶段又因为没时间没有执行。
同一个包两次运行分数差别很大，主要因为每个功能耗时不固定，排在后面的功能会因为没时间被跳过。
